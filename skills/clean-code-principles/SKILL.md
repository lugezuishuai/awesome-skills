# 整洁代码原则（Clean Code Principles）

提炼自 Martin Fowler《重构：改善既有代码的设计（第 2 版）》。这些原则与具体语言无关，
目的是让你在**写代码的当下**就做出更好的结构决策，而不是事后补救。

## 三条心法

写代码前，先把这三件事放在心里——它们解释了下面所有原则“为什么”成立：

1. **代码主要是写给人读的，其次才是给机器执行的。** 几个月后读这段代码、改这段代码的人
   （很可能就是你自己）才是最重要的读者。让代码清楚说出意图，胜过任何聪明的技巧。
2. **好设计是逐步浮现的，不是一开始就定死的。** 不必预先猜中所有需求；先按当前需求把代码
   写清楚，随着理解加深再调整结构。这要求你随时愿意改动已有代码。
3. **用小步、保持行为不变的修改来演进代码。** 每一步都小到不会出错、随时可停。这样你几乎
   不需要花时间调试，也更敢于改进结构。

> 核心准则（Kent Beck）：**每次要修改时，先让这次修改变容易（有时这很难），然后再做这次容易的修改。**

## 写代码时遵循的原则

### 1. 命名要表达意图
名字应清楚说明“它是什么、做什么、怎么用”，让读者不必看实现就能理解。命名是编程中最难的事
之一，也是最值得花时间的事——好名字能省下未来大量“猜谜”的时间。
**信号**：如果你**想不出一个好名字**，往往说明背后藏着更深的设计问题，先把设计理顺。

### 2. 消除重复（DRY）
同一件事如果在多处用相同代码表达，任何修改都得找全所有副本、逐一改对，极易遗漏。
让“每个事实在代码中只表述一次”，这是优秀设计的根本。发现重复就合并：提炼成一个函数，
让各处都来调用它。

### 3. 函数要短小，按“用途”而非“实现”命名
活得最久、最好的程序，函数都比较短。**关键不在行数，而在“做什么（what）”与“如何做（how）”
之间的语义距离**：函数名说清用途，函数体负责实现。
**实操**：每当你想写一行注释来解释某段代码，就把那段代码提炼成一个函数，用它的**用途**命名。
哪怕函数体只有一行、哪怕调用语句比函数体还长，只要名字解释了意图，就值得提炼。

### 4. 控制参数列表
过长的参数列表令人迷惑。总是同时出现的几个参数（“数据泥团”）应合并成一个对象；
能从已有参数查出来的值不必再传；**避免“标记参数”（flag argument）**——它把函数行为
搅在一起，不如拆成两个意图清晰的函数。

### 5. 警惕全局数据与可变数据
全局数据可被任何角落修改且难以追踪，是最刺鼻的坏味道之一；可变数据则常因“一处更新、
别处没料到”而制造诡异 bug。**第一道防线是封装**：用函数包裹数据，把修改入口收拢到少数
几处，再把它的作用域限制到尽量小。能不可变就不可变；派生值用计算得出，不要用可变变量缓存。

### 6. 分离“查询”与“修改”（命令–查询分离）
返回值的函数（查询）不应有可观察的副作用；改状态的函数（命令）不必返回值。
两者混在一起，调用者就无法在“只想读数据”时避开副作用。把无副作用的计算与执行更新的代码分开，
代码会更可预测、更易测试和复用。

### 7. 高内聚、低耦合：把一起变化的东西放在一起
模块化的目标是**最大化区域内交互、最小化跨区域交互**。两个互补的判据：
- **发散式变化**：一个模块因多种不相干的原因被反复修改 → 按关注点拆开，每次只需理解一个上下文。
- **霰弹式修改**：一个改动要在许多模块里东补一刀西补一刀 → 把该一起改的代码聚到一处。
当一个函数频繁取用另一模块的数据（“依恋情结”），就把它搬到数据所在之处——
**数据和操作数据的行为应放在一起**。

### 8. 简化条件逻辑
复杂条件是理解的障碍。把庞大的条件表达式**分解**成有名字的函数；
对“检查后提前返回”的情形用**卫语句（guard clauses）**取代深层嵌套；
当同一套 switch/if 在多处重复、且每加一个分支都要全改一遍时，用**多态**取代它。

### 9. 封装：隐藏细节，善用领域类型
对象的基本价值是对外隐藏内部细节。不要暴露“纯数据类”和裸露的字段；不要让调用方顺着
一长串 `a.b().c().d()` 的消息链导航（一旦结构变化客户端就得跟着改）。
**避免“基本类型偏执”**：钱、坐标、范围、电话号码这类概念，别都用 string/number 硬凑，
给它们建立有意义的领域类型，让校验与显示逻辑有处安放。

### 10. YAGNI：不要为臆想的未来买单
不要用大量“钩子”和参数去迎合“也许将来会用到”的需求——用不上的灵活性只会增加复杂度、
拖慢当下。**只按当前需求构建，但把设计质量做高**；等真正需要时，再用重构加上灵活性
（那时通常很容易）。判断法则：只有当“以后再重构会很困难”时，才值得现在就预留灵活性。

### 11. 自测试代码是一切的基础
能放心地写代码、改结构，前提是有一套**快速、自动化**的测试，一旦出错就立刻失败。
测试让你把排查范围缩小到“上次通过之后改的那几行”。倾向于先写测试（含边界条件），
让测试既验证行为、又表达意图。没有测试的重构是危险的。

### 12. 注释解释“为什么”，而非“是什么”
注释本身是香味而非坏味道，但**常被当作除臭剂**去掩盖糟糕的代码。如果你需要注释来说明
“这段在做什么”，先试着用提炼函数 / 改名让代码自己说清楚。把注释留给真正有价值的地方：
解释**为什么**这样做、记录权衡取舍、标记尚不确定的区域。

### 性能：先清晰，再测量，后优化
不要为臆测的性能到处做牺牲可读性的修改——大部分时间只耗在一小部分代码上，盲目优化九成是白费。
先写清晰、可调优的代码；进入优化阶段后，用度量工具找到真正的热点，针对性优化并每步复测。

## 写代码的工作节奏

- **两顶帽子**：任一时刻，要么在“加功能”（不改结构、用测试驱动），要么在“重构”（不加功能、
  不动行为）。清楚自己戴着哪顶帽子，频繁切换，但不要同时戴。
- **三次法则**：第一次做就做；第二次做类似的事虽有反感也照做；**第三次再遇到，就重构**。
- **见机行事地重构**：在加功能 / 修 bug 的过程中顺手做——
  *预备性重构*（先把地基铺好，让接下来的修改容易）、
  *帮助理解的重构*（边读边把理解固化进代码）、
  *捡垃圾式重构*（至少让营地比你来时更干净）。重构不是与编程割裂的独立阶段。
- **重构的理由是经济性，不是道德洁癖**：我们重构是因为它让我们更快——加功能更快、修 bug 更快。

## 识别坏味道 → 对症重构

“坏味道”是提示“这里可以重构”的信号。写完或读到一段代码时，对照检查；闻到味道后，
选择对应的重构手法小步处理。两份速查：

- **`references/code-smells.md`** —— 24 种代码坏味道：每种的“识别信号”+ 对应的重构手法。
  当你想判断“这段代码哪里不对劲”时读它。
- **`references/refactorings.md`** —— 61 个有名字的重构手法（按 7 大类组织），每个一句话说明
  “做什么、何时用”。当你已知要改、想找具体手法时读它。

> 提醒：不是所有坏味道都必须立刻处理。若一段乱码你并不需要修改、且能被 API 隐藏，可以容忍；
> 只有当你需要理解它、或重写比重构更省时，才另作打算。重构不足远比重构过度常见——多数情况下，应当更主动地重构。
