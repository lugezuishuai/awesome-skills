# 代码坏味道速查（24 种）

提炼自《重构（第 2 版）》第 3 章。坏味道是“这里可能需要重构”的信号，不是必须立刻处理的硬规则——
**培养直觉比死守度量更重要**。每条给出：**识别信号** + **对症重构手法**（手法详见 `refactorings.md`）。

目录：
1. 神秘命名 · 2. 重复代码 · 3. 过长函数 · 4. 过长参数列表 · 5. 全局数据 · 6. 可变数据 ·
7. 发散式变化 · 8. 霰弹式修改 · 9. 依恋情结 · 10. 数据泥团 · 11. 基本类型偏执 ·
12. 重复的 switch · 13. 循环语句 · 14. 冗赘的元素 · 15. 夸夸其谈通用性 · 16. 临时字段 ·
17. 过长的消息链 · 18. 中间人 · 19. 内幕交易 · 20. 过大的类 · 21. 异曲同工的类 ·
22. 纯数据类 · 23. 被拒绝的遗赠 · 24. 注释

---

1. **神秘命名（Mysterious Name）** — 名字看不出用途/用法，读代码像猜谜。
   → 改变函数声明（改名）、变量改名、字段改名。想不出好名字，往往意味着更深的设计问题。

2. **重复代码（Duplicated Code）** — 多处出现相同或近似的代码结构。
   → 提炼函数；近似时先用移动语句把相似部分对齐；子类间重复用函数上移。

3. **过长函数（Long Function）** — 函数太长、要靠注释分段才能读懂。
   → 提炼函数（主力）；以查询取代临时变量、引入参数对象、保持对象完整 缩减参数/临时变量；
   分解条件表达式、拆分循环、以多态取代条件表达式 处理条件与循环。

4. **过长参数列表（Long Parameter List）** — 参数太多，难以理解和调用。
   → 以查询取代参数、保持对象完整、引入参数对象、移除标记参数、函数组合成类。

5. **全局数据（Global Data）** — 数据可被任何角落修改且无法追踪修改者。
   → 封装变量（第一招），再把它搬进类/模块以收紧作用域。

6. **可变数据（Mutable Data）** — 更新数据引发别处意外失效。
   → 封装变量、拆分变量、将查询函数和修改函数分离、移除设值函数、以查询取代派生变量、
   将引用对象改为值对象。

7. **发散式变化（Divergent Change）** — 一个模块因多种不相干原因被反复修改。
   → 拆分阶段、搬移函数、提炼函数、提炼类，按关注点分离上下文。

8. **霰弹式修改（Shotgun Surgery）** — 一个改动要在许多模块里到处改一点点。
   → 搬移函数、搬移字段 把该一起改的聚到一处；函数组合成类/变换；必要时用内联函数/内联类把分散逻辑拽回。

9. **依恋情结（Feature Envy）** — 函数频繁取用另一模块的数据，胜过用自己模块的。
   → 搬移函数（带它去数据所在处）；只有一部分依恋时先提炼函数再搬移。原则：行为与它最常用的数据放一起。

10. **数据泥团（Data Clumps）** — 同样的三四项数据总是成群出现（字段或参数）。
    → 提炼类（字段）、引入参数对象 / 保持对象完整（参数）。检验：删掉其中一项，其余是否还有意义。

11. **基本类型偏执（Primitive Obsession）** — 用 string/number 硬表示钱、坐标、范围、电话号等概念。
    → 以对象取代基本类型；若是控制行为的类型码，用 以子类取代类型码 + 以多态取代条件表达式。

12. **重复的 switch（Repeated Switches）** — 同一套 switch/if 分支逻辑在多处重复。
    → 以多态取代条件表达式。新增分支时不必再到处找、逐一改。

13. **循环语句（Loops）** — 命令式循环掩盖了“在处理什么、做了什么”。
    → 以管道取代循环（map/filter 等），让数据处理一目了然。

14. **冗赘的元素（Lazy Element）** — 函数/类没有提供与其结构相称的价值（如名字与实现雷同）。
    → 内联函数、内联类；继承体系中用折叠继承体系。

15. **夸夸其谈通用性（Speculative Generality）** — 为“也许将来用得到”预留了用不上的灵活性。
    → 折叠继承体系、内联函数/内联类、改变函数声明去掉多余参数；只被测试用到的，移除死代码。

16. **临时字段（Temporary Field）** — 字段仅在特定情况下才被赋值/使用。
    → 提炼类 给它一个家、搬移函数；用 引入特例 取代“变量不合法”的条件判断。

17. **过长的消息链（Message Chains）** — `a.b().c().d()` 让客户端紧耦合于导航结构。
    → 隐藏委托关系；或对链尾对象的用法做 提炼函数 + 搬移函数。

18. **中间人（Middle Man）** — 一个类过半接口只是把调用转发给别人。
    → 移除中间人，直接与真正负责者打交道；少量转发用内联函数。

19. **内幕交易（Insider Trading）** — 模块间私下大量交换数据，耦合过紧。
    → 搬移函数、搬移字段减少私下往来；用隐藏委托关系做中介；继承导致的过度了解用以委托取代子类/超类。

20. **过大的类（Large Class）** — 一个类字段太多、代码太多，重复随之而来。
    → 提炼类、提炼超类、以子类取代类型码；观察使用者只用到哪部分子集来找拆分线索。

21. **异曲同工的类（Alternative Classes with Different Interfaces）** — 做相似的事却接口不一致，无法互换。
    → 改变函数声明 统一签名、搬移函数 对齐协议；若产生重复用提炼超类补偿。

22. **纯数据类（Data Class）** — 只有字段和取值/设值函数，行为放在了别处。
    → 封装记录、移除设值函数；把操作其数据的行为用搬移函数/提炼函数移进来。
    例外：作为不可变的中转结果对象（如拆分阶段的产物）是合理的。

23. **被拒绝的遗赠（Refused Bequest）** — 子类不想要超类的部分实现或接口。
    → 仅不要实现：用函数下移/字段下移给兄弟类。若连接口都拒绝（味道很浓）：以委托取代子类/超类。
    注意：此味道常很淡，不值得每次都处理。

24. **注释（Comments）** — 注释本身是香味，但**常被用来掩盖糟糕代码**。
    → 先用提炼函数 / 改名 让代码自解释；需要说明规格则引入断言。把注释留给“为什么”、权衡与不确定区域。
